# M-Glass App — Системная архитектура

> Этот документ — одновременно промпт для Claude и техническое задание для разработки.
> При любой работе над приложением Claude читает этот файл и строго следует описанной архитектуре.

---

## Суть системы

M-Glass App — внутренняя операционная система компании M-Glass (производство и монтаж зеркал, душевых, стеклянных перегородок).

Система состоит из **четырёх главных разделов**, которые работают независимо, но используют общие данные (AmoCRM, Supabase, калькулятор).

---

## Четыре главных раздела

### 1. Менеджер — `/manager`

**Кто:** Менеджеры по продажам (Яна, Алина, Александра, Семён + новые).

**Суть:** Личный рабочий кабинет менеджера. Только его данные, его задачи, его воронка.

**Функции:**
- Мои активные сделки из AmoCRM (только своя воронка по умолчанию)
- Задачи на сегодня
- Активность за день: звонки, сообщения, перемещения карточек
- Быстрый доступ к калькулятору → КП → отправка клиенту
- Статус сделок: что зависло, что требует действия сегодня

**Права доступа:**
- По умолчанию: видит только свои сделки
- Специальное разрешение (выдаёт Admin): может видеть сделки всей команды
- Разрешения назначаются в `/admin/users` по конкретному пользователю
- Поле в Supabase: `users.can_view_all_deals: boolean`

---

### 2. Admin — `/admin`

**Кто:** Владислав (владелец). В будущем — РОП с ограниченным доступом.

**Суть:** Операционное управление: мониторинг менеджеров, настройки системы, пользователи.

**Функции:**
- **Sales Monitor** — ежедневный отчёт по активности менеджеров (уже реализован, `lib/salesMonitor.ts`)
- **Пользователи** — список менеджеров, роли, разрешения (кому открыть "видеть все сделки")
- **Health Check** — состояние интеграций (AmoCRM, Wazzup, Supabase)
- **AI Control Center** — управление AI-рекомендациями
- **Настройки** — цены, зоны доставки, материалы, услуги

**Связь с другими разделами:**
- Admin видит всё, что видит Менеджер — плюс агрегированные данные по команде
- Настройки из Admin влияют на калькулятор (Коммерческий раздел)

---

### 3. CEO — `/ceo`

**Кто:** Владислав (собственник). В будущем — инвестор или партнёр с read-only доступом.

**Суть:** Стратегический дашборд. Не детали операций, а ключевые метрики бизнеса.

**Функции:**
- Выручка: день / неделя / месяц / год (план vs факт)
- Воронка продаж в целом: количество заявок → конверсия → средний чек → оплаты
- Топ и аутсайдеры по менеджерам (кратко, без деталей — детали в Коммерческом)
- Динамика: рост/падение относительно прошлого периода
- Ключевые риски: зависшие крупные сделки, счета без оплаты
- Прогноз выручки на основе текущего портфеля сделок

**Принцип:**
CEO видит "что происходит с бизнесом", не "кто что делает сегодня".
Минимум цифр, максимум смысла.

---

### 4. Коммерческий — `/commercial`

**Кто:** Владислав + Коммерческий директор + РОП (роль назначается в Admin).

**Суть:** Полная коммерческая аналитика: статистика менеджеров, воронка, планы, КП, деньги.

**Функции:**

#### 4.1 Аналитика менеджеров
- Статистика по каждому: день / неделя / месяц / год
- Метрики: заявок получено, звонков, сообщений, замеров, КП отправлено, счетов, оплат
- Воронка менеджера: конверсия на каждом этапе (заявка → замер → КП → счёт → оплата)
- Зависшие сделки по зонам (как в Sales Monitor, но глубже)
- AI-анализ: что нужно изменить, чтобы менеджер был продуктивнее

#### 4.2 Планирование
- Текущий план менеджера (задаётся вручную или AI предлагает на основе истории)
- Факт vs план в реальном времени
- Прогноз выполнения плана на конец месяца
- AI: на основе исторических данных предлагает реалистичный план на следующий период

#### 4.3 КП и сделки
- Все выставленные КП: статус, сумма, менеджер, клиент
- Счета: выставлен / оплачен / просрочен
- Калькулятор → КП → история расчётов

#### 4.4 Финансы
- Оплаты: поступило за период, ожидается (счета выставлены), остатки
- Маржа по сделкам (себестоимость из калькулятора vs цена продажи)

## Модель доступа

| Раздел | Менеджер (базовый) | Менеджер (расш.) | Admin | CEO | Коммерческий |
|---|---|---|---|---|---|
| `/manager` | ✅ свои данные | ✅ все данные | ✅ | — | — |
| `/admin` | — | — | ✅ | — | — |
| `/ceo` | — | — | ✅ | ✅ | — |
| `/commercial` | — | — | ✅ | ✅ | ✅ |

**Роли в Supabase (`users` таблица):**
```
role: 'manager' | 'admin' | 'ceo' | 'commercial'
can_view_all_deals: boolean  — для менеджеров с расширенным доступом
```

Один пользователь может иметь несколько ролей (например, РОП = `commercial` + `admin`).

## Источники данных

| Данные | Источник | Кто читает |
|---|---|---|
| Сделки, этапы, менеджеры | AmoCRM API v4 (GET only) | Все разделы |
| КП, расчёты, история | Supabase (`calculations`, `order_groups`) | Менеджер, Коммерческий |
| Пользователи, роли | Supabase (`telegram_users`) | Admin |
| Звонки, сообщения | AmoCRM Notes API | Менеджер, Коммерческий |
| Финансы, оплаты | AmoCRM (статусы сделок) + Supabase | Коммерческий, CEO |

AmoCRM — только READ. Никаких POST/PATCH к сделкам, карточкам, задачам.

## Приоритеты разработки

1. **Менеджер** (`/manager`) — личный кабинет с воронкой и задачами на день
2. **Коммерческий** (`/commercial`) — аналитика менеджеров день/неделя/месяц/год + планы
3. **CEO** (`/ceo`) — стратегический дашборд с прогнозами
4. **Права доступа** — роли в Supabase, управление из Admin

---

## Принципы, которые нельзя нарушать

1. **AmoCRM — только чтение.** Ни одного POST/PATCH к CRM.
2. **Данные одного менеджера недоступны другому** без явного разрешения Admin.
3. **Все зоны воронки** определяются строго по таблице выше — не придумывать новые.
4. **Один источник правды для метрик** — если данные есть в AmoCRM, не дублировать в Supabase.
5. **Каждый раздел — отдельный маршрут** (`/manager`, `/admin`, `/ceo`, `/commercial`). Не смешивать логику разделов.
