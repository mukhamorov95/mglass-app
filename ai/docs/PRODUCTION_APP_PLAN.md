## 1. Зачем нужен Production App

`/b2b-orders` — управленческая страница для менеджеров и руководства. Она содержит коммерческую информацию, сложные фильтры и действия, которые производственным рабочим не нужны и были бы источником путаницы.

**Основная цель Production App:**  
Каждый сотрудник видит только свои задачи и отмечает выполнение этапов по заказу / детали / операции. Интерфейс простой, быстрый, работает с телефона.

**Проблемы, которые решает приложение:**
- Рабочим неудобно и незачем заходить в `/b2b-orders`
- Менеджер не видит производственный статус без звонка Никите
- Нет возможности фиксировать проблемы (скол, царапина, нет материала) централизованно
- Руководитель не видит, на каком этапе завис конкретный заказ

---

## 2. Почему PWA, а не native app на первом этапе

**Первый этап — web/PWA внутри текущей системы.**

Рабочий открывает ссылку с телефона и добавляет её на главный экран (как нативное приложение). Это:

- **Быстрее** — не нужен App Store / Google Play, обновления мгновенные
- **Дешевле** — один кодобаз для iOS и Android
- **Безопаснее** — не надо проходить модерацию Apple/Google при изменениях
- **Достаточно** — PWA даёт push-уведомления, оффлайн-кеш, работу в полноэкранном режиме

**Путь к native app** (если потребуется) — через Capacitor/Expo поверх готового PWA. Но это не шаг 1.

## 3. Связь с текущей системой

### Текущая основа

| Компонент | Назначение |
|---|---|
| `/b2b-orders` | Управленческий экран заказов (менеджеры, руководство) |
| `production-sheet` | Печатный производственный лист + QR-код |
| `/p/o/{id}` | Текущий мобильный QR-интерфейс отметки этапов |
| `notes.detail_stages` | Хранение отметок этапов по деталям внутри заказа |
| `notes.stages` | Этапы на уровне заказа (packaged, shipped, invoice_paid…) |

### Новая модель

Production App **не создаёт отдельную базу данных**. Он использует те же `b2b_orders` и производственные статусы, но показывает их в отдельном простом интерфейсе.

Запись производственных отметок идёт в `notes.detail_stages` и `notes.stages` — туда же, куда пишет `/b2b-orders` и `/p/o/{id}`. Единый источник правды — Supabase.

## 4. Роли

### CEO / Владелец

- Видит все заказы в производстве
- Контролирует сроки, просрочки, узкие места
- Видит агрегированную сводку: сколько в работе, сколько просрочено, где проблемы

### Начальник производства

- Видит все производственные заказы, этапы, проблемы, просрочки
- Может назначать приоритеты
- Фиксирует проблемы и подтверждает готовность
- Видит полную панель: где завис каждый заказ

### Производственный ассистент / координатор (Никита)

- Видит все заказы в работе
- Помогает фиксировать этапы
- Контролирует закалку, упаковку, проблемы, готовность
- Может редактировать производственные статусы за рабочих

### Менеджер продаж

- Видит **только производственный статус** для коммуникации с клиентом:
  - в работе
  - на каком этапе
  - срок
  - есть ли риск
  - готово / не готово
- **Не может** менять производственные этапы
- Не видит себестоимость, маржу и другую коммерческую информацию производства

### Офис-менеджер

- Видит статусы, готовность, отгрузки
- Может помогать фиксировать данные
- Без лишней коммерческой сложности

### Производственник (рабочий)

- Видит **только свои задачи** по своей зоне (резка / сверловка / упаковка и т.д.)
- Может:
  - отметить этап выполненным
  - создать проблему с причиной
  - добавить короткий комментарий

## 5. Производственные отделы / операции

Возможные рабочие зоны:

| Зона | Описание |
|---|---|
| Резка | Раскрой листов по размерам |
| Полировка | Обработка торцов |
| Сверловка | Отверстия под крепёж |
| Вырезы | Фигурные вырезы, пазы |
| Фацет | Фацетная обработка |
| Закалка / подготовка | Подготовка к закалке, отправка, получение |
| Триплекс | Склейка листов |
| Упаковка | Упаковка готовых деталей |
| Отгрузка | Передача клиенту / монтажной бригаде |

> **MVP-принцип:** Не все зоны должны быть отдельными ролями в MVP. На первом шаге достаточно общего «производственника» с возможностью указать зону операции при отметке. Специализированные роли по зонам — в будущих итерациях.

## 6. Основные экраны приложения (MVP)

### Главный экран — «Сегодня»

```
Сегодня
├── Мои задачи (N)
├── Просрочено (N)
├── Проблемы (N)
└── Готово к упаковке (N)
```

Быстрый обзор для рабочего. Минимум информации — максимум ориентации.

### Мои задачи

Карточки заказов и деталей, отсортированные по приоритету и сроку. Каждая карточка показывает:
- Номер заказа
- Клиент (сокращённо)
- Срок
- Текущий этап
- Кнопка «Отметить»

### Экран заказа

```
Заказ #00590 — LoLegko
Срок: 18 июня
─────────────────────
Деталь 1: 800×600, 6мм
  [✓] Резка
  [✓] Полировка
  [ ] Упаковка  ← активный этап

Деталь 2: 400×300, 6мм
  [✓] Резка
  [ ] Полировка  ← активный этап
─────────────────────
[⚠ Создать проблему]
```

Без коммерческой перегрузки (нет цен, нет маржи, нет статусов оплаты).

### Экран проблемы

Рабочий нажимает «Создать проблему» и выбирает причину:

```
Нет материала
Скол
Царапина
Не тот размер
Нужен чертёж
Не понятно ТЗ
Брак после закалки
Другое
```

Опционально — короткий текстовый комментарий. Проблема появляется у ассистента и начальника производства.

### Панель начальника производства

```
Все заказы (N)
├── Просрочено (N) 🔴
├── Где зависло (N) 🟠
├── Проблемы (N) ⚠
├── Готово (N) ✅
└── Сегодня (N) 🟡
```

Каждый заказ раскрывается в полный список деталей и этапов.

## 7. Базовый workflow

```
1. Заказ запускается в работу из /b2b-quotes
        ↓
2. Заказ появляется в /b2b-orders
        ↓
3. Создаётся производственный список деталей
   (из b2b_orders.items)
        ↓
4. Для деталей определяются нужные этапы
   (на основе категории материала / услуг)
        ↓
5. Рабочий открывает Production App
        ↓
6. Видит свои задачи на сегодня
        ↓
7. Отмечает этап выполненным
   → записывается в notes.detail_stages
        ↓
8. Следующий этап становится активным
        ↓
9. Ассистент/начальник видят актуальный прогресс
        ↓
10. Менеджер видит понятный статус для клиента
    (без производственных деталей)
```

## 8. Интеграция с QR

| Компонент | Роль |
|---|---|
| `/p/o/{id}` | Остаётся **быстрым QR-интерфейсом**: отсканировал → отметил этап |
| Production App | **Полноценное рабочее приложение** со списком задач, историей, проблемами |

В будущем `/p/o/{id}` можно визуально привести к дизайну Production App или встроить как deeplink. На этапе MVP они работают параллельно и пишут в одну структуру (`notes.detail_stages`).

---

## 9. Что НЕ делаем в MVP

| Что не делаем | Почему |
|---|---|
| Native app (App Store / Google Play) | Долго, дорого, PWA достаточно |
| Сложную аналитику и KPI | Не нужно на старте |
| Сломать `/b2b-orders` | Это разные слои: управление vs производство |
| Менять структуру `notes` прямо сейчас | Текущей достаточно для MVP |
| Сложную систему смен | Не нужно на старте |
| Требовать от рабочих много ввода | Максимум: выбор из списка + 1 строка |
| Отдельные роли по каждой зоне сразу | Сначала один «производственник» |

### Шаг 2 из 10 — Skeleton /production-app

**Что:** Создать маршрут `app/production-app/` с базовой структурой страниц.
- `app/production-app/page.tsx` — главный экран (пустой skeleton)
- `app/production-app/layout.tsx` — layout с мобильным viewport
- `app/production-app/orders/[id]/page.tsx` — страница заказа (пустой skeleton)
- Базовый auth-check (только роли: `production`, `admin`, `ceo`)
- Добавить ссылку в Sidebar для нужных ролей

**Критерий готовности:** Маршруты открываются, auth работает, остальные разделы не сломаны.

---

### Шаг 3 из 10 — Базовые роли и доступ

**Что:** Настроить доступ для роли `production` в Supabase и UI.
- Убедиться, что роль `production` существует в `users.role`
- `production`-пользователь попадает только в `/production-app`, не в `/b2b-orders`
- Страница `/production-app` недоступна без авторизации
- Sidebar показывает нужные пункты в зависимости от роли

**Критерий готовности:** Пользователь с ролью `production` видит только Production App.

---

### Шаг 4 из 10 — Главный экран «Сегодня»

**Что:** Реализовать главный экран с реальными данными.
- Загрузить активные заказы из `b2b_orders`
- Показать счётчики: Мои задачи / Просрочено / Проблемы / Готово к упаковке
- Карточки заказов отсортированы по сроку
- Читать из `notes.stages`, `notes.detail_stages`

**Критерий готовности:** Экран показывает реальные заказы, счётчики актуальные.

---

### Шаг 5 из 10 — Экран заказа и деталей

**Что:** Реализовать `orders/[id]/page.tsx`.
- Показать список деталей из `b2b_orders.items`
- Для каждой детали — список этапов с чекбоксами
- Кнопка «Отметить» сохраняет в `notes.detail_stages`
- Без цен, маржи, оплат

**Критерий готовности:** Рабочий может открыть заказ и отметить этап одним нажатием.

---

### Шаг 6 из 10 — Интеграция с QR /p/o/{id}

**Что:** Убедиться, что QR-интерфейс и Production App пишут в одну структуру.
- Проверить, что `/p/o/{id}` и Production App не конфликтуют при записи `detail_stages`
- При необходимости — унифицировать формат данных
- Опционально: QR-кнопка на экране заказа Production App

**Критерий готовности:** Отметка через QR видна в Production App и наоборот.

---

### Шаг 7 из 10 — Проблемы / брак

**Что:** Реализовать экран фиксации проблем.
- Список причин: Нет материала / Скол / Царапина / Не тот размер / и т.д.
- Сохранение в `notes` (в поле `production_issues[]` или аналогичном)
- Проблемы видны на панели начальника производства
- Опционально: push/toast-уведомление ассистенту

**Критерий готовности:** Рабочий может зафиксировать проблему за 3 нажатия.

---

### Шаг 8 из 10 — Панель начальника производства

**Что:** Реализовать отдельный view для ролей `admin`, `ceo`, `production` (с правами просмотра всего).
- Все заказы в производстве
- Секции: Просрочено / Где зависло / Проблемы / Готово / Сегодня
- Возможность раскрыть заказ и увидеть детали/этапы
- Фильтрация по зоне/операции

**Критерий готовности:** Начальник видит полную картину без захода в `/b2b-orders`.

---

### Шаг 9 из 10 — Уведомления / контроль

**Что:** Добавить базовую систему алертов.
- Заказ просрочен → появляется в разделе «Просрочено»
- Проблема зафиксирована → уведомление (toast / Telegram) ассистенту
- Заказ готов → уведомление менеджеру
- Опционально: push через Web Push API (PWA)

**Критерий готовности:** Ключевые события не теряются, команда получает сигнал.

---

### Шаг 10 из 10 — PWA установка на телефон

**Что:** Настроить приложение как полноценный PWA.
- `app/production-app/manifest.json` с иконкой MGlass
- `service-worker` для оффлайн-кеша статических ресурсов
- `<meta name="theme-color">` для мобильного браузера
- Инструкция «Добавить на экран» при первом входе
- Проверка на iOS Safari и Android Chrome

**Критерий готовности:** Рабочий добавил ссылку на экран телефона, приложение выглядит как нативное.
