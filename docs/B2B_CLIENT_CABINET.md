# Личный кабинет B2B-заказчика — архитектура

> Авторитетная спецификация. Ветка `feat/b2b-client-cabinet` (изолированный worktree
> `mglass-b2b-cabinet`, база — `main`). Внешний контур: сюда логинятся клиенты компании.
> Требование №1 — **изоляция данных**: один заказчик никогда не видит чужое.

## 1. Цель

Дать основным B2B-заказчикам личный кабинет, связанный с нашей программой, где клиент:
- входит под своим паролем (усиленная безопасность, полная изоляция);
- видит **свои** заказы по стадиям: просчёт → в работе → отгружен;
- видит **табло** за год: число заказов, сумма, средний чек, что сейчас в работе;
- сам считает детали (стекло/зеркало) в B2B-калькуляторе, сохраняет и отправляет нам в работу;
- скачивает документы (КП, счёт-спецификация);
- получает уведомления о смене статуса.

Внедрение — **пилот** на 2-3 основных клиентах, затем массовая выдача доступа.

## 3. Связь с программой (data flow)

Одна таблица `b2b_orders` — и просчёт, и заказ. Различие: `notes.status` (JSON) + `launched_at`.
Позиции — в `items` (JSONB). Источник — `source='partner'`.

```
Кабинет /partner                         Программа (менеджер → цех)
──────────────────                       ────────────────────────────
/partner/new  calcItem (сервер) ─ save ─► b2b_orders (source='partner',
                                          notes.status='quote')
«Отправить в работу» ───────────────────► notes.status='pending_approval'
                                          → менеджер видит в /b2b-quotes
                                          → «Запустить» → launched_at +
                                            production_tasks (цех, стадии)
Ленты «Мои заказы» ◄──────── статусы из notes.stages / launched_at / archived_at
```

Стадии производства (`notes.stages`): `printed → material_ordered → cut → edge →
drilled → tempering → packed → shipped`. Кабинет показывает % и текущий этап.

## 4. Модель безопасности (три рубежа)

Изоляция клиентов — приоритет. Текущая изоляция держится на коде; усиливаем до
defense-in-depth. **Правило: заказчик получает данные ТОЛЬКО через серверные
`/api/partner/*`; `client_id` всегда выводится из `auth.uid()`; вход клиента не доверяем.**

### Рубеж 1 — Единственная дверь (приложение)
- Все чтения/записи клиента идут через `/api/partner/*` (service-role) с фильтром по
  `auth.uid() → b2b_clients.id`. Прямого доступа браузера к таблицам у клиента нет.
- Наружу — только «безопасная проекция» (цена клиента), никогда `cost`/`margin`.
- Роль `partner` в allowlist — только `['/', '/partner']`. Аудит: все внутренние API
  (`/api/b2b-orders/[id]/*`, `/api/admin/*`, и т.д.) обязаны **отклонять** роль `partner`.

### Рубеж 2 — RLS-бэкстоп (база, deny-by-default)
- Даже при прямом обращении к БД партнёр видит строки только где
  `b2b_clients.user_id = auth.uid()` / `b2b_orders.client_id ∈ (свои client_id)`.
- **Закрыть дыру `auth.org_id() COALESCE(...,1)`**: партнёр не должен попадать в org=1.
  Каждому партнёру — отдельная организация (или явный deny org-политики для роли partner).
- Проверить: `USING(true)`-политики не открывают клиенту лишние таблицы.

### Рубеж 3 — Вход и аудит
- Пароли — только Supabase Auth (хеши). `password_plain` для клиентов **не используем**.
- Лог входов/значимых действий в `security_events`. Сильные пароли, самостоятельная смена.
- 2FA-код при входе — заложено на будущее (флаг), в пилоте не обязателен.
- Выдача доступа — через одноразовую ссылку `set-password` (пароль знает только клиент).

## 5. Модули кабинета

| Модуль | Маршрут | Состояние |
|---|---|---|
| Мои заказы (ленты) | `/partner` | есть; + переход в карточку |
| **Карточка заказа** | `/partner/order/[id]` | новое: позиции, размеры, чертёж, история статусов, срок |
| **Табло за год** | `/partner` (верхний блок) или `/partner/dashboard` | новое: кол-во заказов, сумма, средний чек, в работе, график по месяцам |
| Калькулятор (детали) | `/partner/new` | есть; + история просчётов, вложение чертежа |
| **Документы** | из карточки заказа | новое: КП + счёт-спецификация (реквизиты в `b2b_clients`) |
| **Уведомления** | фон | новое: партнёру — смена статуса; менеджеру — новая заявка |
| **Инструкция / регламент** | `/partner/guide` | новое: как пользоваться кабинетом и работать с нами (пошагово, для клиента) |
| Смена пароля / выход | `/partner` | есть |

Калькулятор в кабинете считает **детали стекла и зеркала** (размер, толщина, закалка,
фацет, отверстия). Готовые изделия (душевые/лофт) — вне пилота.

## 5a. Бренд кабинета

Кабинет — внешняя точка контакта клиента с M-Glass, поэтому носит фирменный стиль:
- **Акцент (кнопки, активное меню):** терракотовый `#c0453a` (тёмная тема `#d3564a`), текст на нём белый.
- **Знак «М»:** двухтоновый (свет `#d0574a` / тень `#9c3529`) — отражение в стекле.
- **Статусы заказов** (синий/янтарный/зелёный/серый) — отдельно от бренда, кодируют стадию.
- Нейтральная база (`#f0f0ec` фон, `#111110` текст) — как в основном приложении.

## 6. Изоляция ветки и БД

- **Код** — изолированный worktree `mglass-b2b-cabinet`, ветка `feat/b2b-client-cabinet`
  от `main`. Другие ветки не затрагиваются; коммитим только файлы кабинета.
- **База Supabase — общая на все ветки** (один проект). Поэтому: изменения схемы
  **строго аддитивные** (новые колонки/политики, ничего не ломаем у внутренних).
  Миграции пишем файлами; применяем вручную (конвенция репозитория). Для рискованных
  изменений доступна отдельная ветка БД Supabase (нулевой риск для прода).

## 7. Дорожная карта (пилот → массово)

**Фаза 0 — Безопасность и провижининг (фундамент пилота)**
1. RLS-бэкстоп: реальная изоляция partner по `user_id`, закрыть дыру org=1 (аддитивная миграция).
2. Аудит внутренних API: убедиться, что роль `partner` отклоняется везде, кроме `/api/partner/*`.
3. Админ-выдача доступа: создать auth-учётку + привязать `b2b_clients.user_id` + ссылка
   `set-password` (переиспользовать `invite-link`/`set-password`). UI в `/admin`.
4. Лог входов/действий партнёра в `security_events`.

**Фаза 1 — Ценность для клиента**
5. Табло за год (KPI + график) в кабинете.
6. Карточка заказа `/partner/order/[id]`: позиции, чертёж, история статусов, срок.
7. Документы: скачивание КП и счёт-спецификации из кабинета.

**Фаза 2 — Полировка и обкатка**
8. Уведомления (партнёру о статусе, менеджеру о заявке).
9. Калькулятор: история просчётов, вложение чертежа, повтор заказа.
10. Пилот на 2-3 клиентах, сбор обратной связи.

**Фаза 3 — Массовость**
11. Массовая выдача доступа, онбординг-инструкция для клиента.
