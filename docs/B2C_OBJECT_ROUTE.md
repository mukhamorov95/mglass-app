# Маршрут: объект M-Glass от заявки до сдачи

Задача владельца (22.11.2026): навести порядок во всей рознице M-Glass (B2C). Нужно:

* учесть все продажи;
* менеджер видит все свои объекты;
* отдел реализации ведёт каждый объект, и у каждого посчитана маржа;
* закупка материала: что нужно, откуда забрать, маршрут забора строится сам;
* весь путь от заявки до успешно сданного объекта.

Маршрут продолжает `docs/B2C_CRM_ROUTE.md`. Там С1–С9 переносят приём заявок и воронку из amo (заявка → продажа). Здесь — продажа → сдача объекта. Сшиваются они номером заказа.

## Цель

Готовность проверяется четырьмя вопросами. На каждый человек отвечает с одного экрана за минуту:

1. **Владелец:** сколько объектов в реализации, на какой стадии каждый, у каких не посчитана маржа.
2. **Менеджер:** мои объекты — что оплачено, что ждёт, когда монтаж.
3. **Отдел реализации:** что сегодня заказать, забрать и смонтировать, и по какому объекту.
4. **Водитель или закупщик:** куда ехать сегодня и в каком порядке.

**Главное:** продажа — единственное звено, которое учитывается полностью (книга владельца). Поэтому **объект = строка продажи с номером заказа**. К ней по номеру цепляются сделка amo, маржа, монтаж, материал и сдача. Вторую сущность «заказ» рядом не строим: `orders` и `deals` пусты.

## Этапы

Каждый этап — один PR и точка остановки. Порядок — по отдаче: сначала видно всё, что уже есть, потом добавляется новое.

### Р1. Реестр объектов — то, что уже есть, на одном экране
`/realization`: каждая продажа M-Glass с 01.08 — строка объекта. Стадия выводится из данных:
* в работе / монтаж назначен / смонтирован / сдан;
* остаток оплачен или нет;
* маржа посчитана или нет — **только отметкой, без цифр**;
* монтаж (дата, бригада).

Фильтры: менеджер, стадия, «без маржи», «без монтажа». Плитки вверху: в реализации N, без маржи N, монтажей на неделе N. Только чтение, новых таблиц нет.
**Проверка:** 79 открытых и 39 закрытых совпадают с замером выше.

### Р2. Менеджер видит свои объекты
Вкладка «Мои объекты» в кабинете менеджера. Фильтр по `crm_sales.manager` ↔ имени пользователя (сопоставление в одной функции, с тестом на всех нынешних именах). Чужие объекты не видны, пока нет `can_view_all_deals`. Сумма и оплаты видны, себестоимость — нет.
**Проверка:** вход под менеджером — только свои; под владельцем — все.

### Р3. Маржа каждого объекта
Цифры маржи остаются в CFO и `/sales/margin` (`canMargin`). В реестре — только отметка «не посчитана», переход по ней ведёт в `/sales/margin` на этот заказ. Ввод себестоимости поверх книги уже есть (`margin_edits`, право Веры).
* Неделя без внесённой себестоимости → объект в списке «посчитать маржу».
* Синк книги ругается, если для месяца продаж нет вкладки (сейчас ноябрь).

**Проверка:** число «без маржи» = 23 за авг–окт + ноябрь, пока владелец не завёл вкладку.

### Р4. Связь с заявкой
Продажа ↔ сделка amo по номеру заказа или полю сделки (только GET). Даёт путь «заявка → продажа → сдача» и сроки каждого шага. Когда С3 перенесёт сделки в приложение, связь переходит на свою базу.
**Проверка:** доля связанных объектов; несвязанные — списком.

### Р5. Монтажи сами из календаря
Крон синхронизирует календарь монтажей (сейчас импорт был разовый). Выезд привязывается к объекту по номеру заказа; выезды без номера — в список «привязать».
**Проверка:** выезды после 15.10 появились, связано ≥ 80 %.

### Р6. Материал объекта
У объекта список позиций к закупке: что, сколько, у кого (поставщик из справочника с адресом забора), статус заказать → заказано → забрать → на месте. Позиции берутся из расчёта, если он есть, иначе вводятся вручную. Справочник поставщиков: название, адрес, часы, контакт.
Заявки поставщикам система **не отправляет**, только хранит отметки (как в B2B, `docs/PURCHASING_ROUTE.md`).
**Проверка:** на 5 живых объектах список заведён, отдел реализации подтверждает, что он совпадает с реальностью.

### Р7. Маршрут забора
Лист дня: все позиции «забрать» по поставщикам. Порядок объезда считает код (ближайший сосед от цеха в Мытищах, координаты поставщиков в справочнике). Кнопка открывает маршрут в Яндекс Картах (`rtext=` со всеми точками), для телефона водителя.
**Проверка:** лист на реальный день и маршрут, который водитель признаёт разумным.

### Р8. Сдача и сквозной отчёт
«Сдан» = монтаж закрыт + остаток оплачен (+ фото в архиве «Монтажи», если найдено). Отчёт: объекты по стадиям, сроки «продажа → монтаж → сдача», зависшие сверх нормы.
**Проверка:** сданные за октябрь совпадают с книгой владельца.

## Решения владельца

1. **Кто отдел реализации.** Кто эти люди (роль в приложении) — новая роль или право у существующих (Вера — `buyer`)?
2. **Объект = продажа из книги по номеру заказа.** Строим всё на этом, отдельную сущность «заказ» не заводим.
3. **Себестоимость.** Продолжаем вести книгу маржи в Google-таблице (тогда нужна вкладка «Ноябрь 26»), или с декабря вносим себестоимость в приложении?
4. **Поставщики для забора.** Список точек, откуда забирают розницу: стекло и закалка, фурнитура, зеркала, профиль. Название и адрес — остальное заведу сам.
5. **Календарь монтажей.** Синхронизировать его каждый день (Р5)?
6. **Кто видит маржу объекта.** Предлагается: владелец, CFO, Вера. Отдел реализации и менеджер видят только «посчитана / нет».

## Риски

* Имя менеджера в книге — текст. Разное написание прячет объекты от менеджера. Сопоставление в одной функции с тестом; несопоставленные имена видит владелец.
* Номер заказа в календаре вписан руками. Часть выездов не привяжется — для них отдельный список.
* Книга владельца остаётся источником продаж. Правка в таблице после синка появится в приложении только со следующим синком.

## Потолок

* Маршрут не отправляет заказы поставщикам и не пишет в amo.
* Порядок объезда — эвристика без пробок. Яндекс Карты перестроят его с учётом пробок при открытии, но код пробок не знает.
* Пока продажи вносятся в Google-таблицу руками, объект появляется в приложении только после записи в книгу. Автоматически из сделки amo — после С3/С7 маршрута CRM.
