## 🔗 Контракт между сессиями — тип `Quantities` (lib/configurator/pricing.ts:15)
Это шов. Сайт/3D гарантирует корректный `Quantities` из модели; Прайс гарантирует корректный
`PriceResult` из `Quantities`+`UnitPrices`.
```
computeQuantities(assembly, thickness) → Quantities   // владелец: Сайт+3D (геометрия)
computePrice(quantities, unitPrices, opts) → PriceResult // владелец: Прайс (математика)
```
**Правило:** менять поля `Quantities`, `UnitPrices`, `PriceResult`, роли (`rolesFrom`) или
ключи геометрии фурнитуры — только с записью в лог ниже и, по возможности, пингом второй сессии
(SendMessage). Кто меняет форму контракта — предупреждает.

### ⚠️ Критично: коды фурнитуры → PLACEMENT_ROLE (в kit.ts)
Прайс сопоставляет код точки установки из геометрии (`HardwarePlacement.model`) с ролью в прайсе:
`balge/dessau→петля, sd210→ручка, kupe→ручка-купе, roller→ролик, kp002→крепёж к стене,
kp006→к стеклу, kp001→угловое, connector→соединитель, cap→заглушка`.
**Если я добавляю НОВЫЙ код в `HardwarePlacement.model` или меняю смысл существующего — обязателен пинг
Прайсу.** Иначе новая фурнитура молча посчитается по нулю и изделие уедет клиенту ДЕШЕВЛЕ себестоимости.

### Будущее (не срочно): различение двери в геометрии
Сейчас распашная/раздвижная различается только по `MModel.runs` — Прайс выводит сам. Когда буду трогать
`GlassPart.role`, добавлю различение `'door'` (распашная) / `'slide'` (раздвижная) — Прайс перейдёт на него.

### Будущее: шов изменится на клиентском выборе
Когда Прайс сделает `/api/configurator/options` с вариантами по ролям для конкретной модели и выбор
клиента (кол-во петель 2/3 + конкретная позиция, а не только shape) — **формат контракта согласуем ДО**
того, как что-то тронет `ConfiguratorClient`. Прайс в `components/configurator/**` не пишет, отдаёт мне
готовый contract + данные, интеграцию в UI делаю я.
