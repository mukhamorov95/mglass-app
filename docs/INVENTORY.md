# Склад — как устроен

Раздел `/inventory`. Один реестр остатков на оба контура: B2B (стекло, зеркало) и B2C (фурнитура,
профиль, уплотнители, расходники).

## Главное правило

**Остаток — это сумма движений, а не поле, которое кто-то правит.**
`inventory_items.qty` ведёт триггер по `inventory_moves`. Журнал неизменяем: ошибка исправляется
встречным движением, а не редактированием записи. Поэтому на любой вопрос «почему столько» есть
ответ: кто, когда, по какому документу.

До этого остаток жил тремя полями в трёх справочниках (`materials.stock_qty`,
`shower_catalog_items.stock_qty`, `b2b_materials.stock_sheets`) — все три были нулевые и ничем не
подтверждались. Страницы `/admin/warehouse` и `/admin/stock-control` теперь редиректят на `/inventory`;
старые колонки в справочниках больше не пишутся.

## Единицы

У позиции есть **базовая единица** (`unit`) и необязательная **тара** (`pack_label` + `pack_size`).

| Что | База | Тара | pack_size |
|---|---|---|---|
| Стекло, зеркало | м² | лист | площадь листа: 3210×2250 → 7.2225 |
| Профиль, штанга, уплотнитель | м.п. | хлыст | длина хлыста в метрах: 2200 мм → 2.2 |
| Фурнитура | шт | — | 0 |

Человек вводит листы и хлысты, база хранит м² и м.п. Пересчёт — `lib/inventory/units.ts`
(`packToBase` / `baseToPack`), формат для показа — `describeQty`.

## Откуда берутся движения

| Событие | Реализация | reason |
|---|---|---|
| Приход накладной | вкладка «Приход», можно от закупки (`purchase_orders`) | `purchase` |
| Списание в B2B-заказ | `b2b_orders.items` → `materialId` + `totalAreaBilled` (м² **с раскроем**) | `order` |
| Списание в B2C-заказ | `order_lines.materials_bom` / `hardware_bom` по названию | `order` |
| Инвентаризация | вкладка «Инвентаризация»: вводится факт, разницу пишет система | `count` |
| Ручной приход/расход | кнопки «+» / «−» в таблице остатков | любой |

**Списание всегда по кнопке и после предпросмотра.** Система показывает, что уйдёт и хватает ли
остатка; молча склад не уменьшается. Повторное списание по тому же документу блокирует уникальный
индекс `inventory_moves_doc_item_uniq`.

## Сопоставление названий

B2C-состав заказа (`materials_bom`) хранит только имя строкой. Порядок поиска складской карточки:
`ref_table/ref_id` (жёсткая ссылка на справочник) → `bom_aliases` → нормализованное имя.
Непонятые строки видны в предпросмотре: их можно привязать к позиции прямо там — название уедет
в `bom_aliases`, и дальше заказ узнаётся сам. Услуги (монтаж, доставка, работа) со склада не списываются.

## Доступ

- Смотрят: `admin`, `ceo`, `buyer`, `production`, `manager`, `commercial`, `cfo`
- Двигают остатки: `admin`, `ceo`, `buyer`, `production`
- Видят себестоимость и стоимость запаса: `admin`, `ceo`, `buyer`, `cfo` — остальным поля обнуляются
  на выходе из API, а не прячутся в вёрстке

RLS на обеих таблицах включён без политик: браузер к складу напрямую не ходит, только через
`/api/inventory/*` на service-роли.

## Себестоимость

`avg_cost` — скользящая средняя за базовую единицу, двигается только приходом с ценой.
Стоимость запаса = `qty × avg_cost`. Это цифра для CFO, к прайсам и марже отношения не имеет.

## Резерв под заказ (С4)

При запуске заказа материал **резервируется**, а не списывается: `qty_reserved` растёт,
`qty` не меняется, доступное = `qty − qty_reserved`. Резерв ≠ расход — списание в цех остаётся
отдельным движением по кнопке (`applyConsume`), и оно закрывает резерв (`status → consumed`),
чтобы материал не считался дважды.

Контракт для запуска производства (`lib/inventory/reserve.ts`):

```
reserveForOrder(docType, docId, items) → { reserved[], shortages[], alreadyReserved }
```

- **best-effort**: позиции нет в номенклатуре или не хватает — это `shortage`, а не ошибка;
  вызывающий (launch-production) не должен падать из-за склада
- **идемпотентно**: повторный запуск того же заказа не удваивает резерв (`alreadyReserved=true`)
- `shortages` → «что докупить», `reserved` → «что забрать со склада»
- снятие резерва — `releaseReservation` (отмена/перепросчёт), склад не трогается
- ledger: `inventory_reservations`, `qty_reserved` ведёт триггер

HTTP-обёртка для тех же операций — `/api/inventory/reserve` (POST резерв / GET список / DELETE снять).
