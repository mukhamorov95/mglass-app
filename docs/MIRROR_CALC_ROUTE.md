## 0. Что нашли в старом (правило «старое под сомнением», WORKING_RULES §2.0)

Разбор перед стройкой, а не после. Три находки, все — деньги или доступ.

**1. Живой калькулятор зеркал берёт зеркало по ПРОДАЖНОЙ цене как себестоимость.**
`lib/mirrorCalculator.ts` читает sale-строку матрицы (`mirrorCostPerM2`), и на неё сверху
накидывается маржа. Это двойная маржа: цена клиенту завышена. V2-движок
`lib/pricing/calculateMirrorUnified.ts` читает cost-строку — то есть правильный вариант
уже написан и работает в B2B-калькуляторе, но менеджерский экран считает старым.

**2. Подсветка считается по ВСЕМУ периметру.** Лента, профиль и рассеиватель умножаются
на периметр зеркала, даже если свет идёт по одной стороне. В V2 для этого есть
`lightingLengthM(w, h, sides)` — по выбранным сторонам. Старый экран его не зовёт.

**3. Себестоимость уходит в браузер.** `/calculator/mirror` тянет `cost_price` всех
справочников (лента, БП, рамки, услуги) прямо в клиент. У душевых этого нет: цену считает
сервер (`/api/calc/build`), наружу идёт только результат. Для зеркал серверного роута нет
вообще.

Плюс хардкоды-фолбэки в старом движке: датчик 800, кнопка 400, пескоструй 1200,
сложная форма 1500 — числа в коде, а не в справочнике.

**Вывод:** старый экран (1796 строк) не переиспользуем. Ядром берём `calculateMirrorUnified`,
старый закрываем, когда новый закроет его случаи (`quickCalc.ts` пока на нём — трогаем последним).

## Что берём как есть

| Кусок | Почему годится |
|---|---|
| `calcFinancialModel` | единая точка наценки для всех продуктов |
| `calculateMirrorUnified` | cost-only, без двойной маржи, с упаковкой/браком/накладными |
| `lightingLengthM` + `LightSides` | готовая модель «подсветка по сторонам» |
| `calcFrameCost` | считает ЦЕЛЫЕ хлысты профиля — единственная честная кратность в проекте |
| `planBars` (kit.ts) | образец раскроя с пропилом и сращиванием — для ленты и профиля |
| `mirror_lighting_components`, `mirror_frames`, `mirror_frame_rates`, `facet_prices` | схема адекватная, менять не надо |
| `supplier_price_rows` (`cost = retail × (1−скидка)`) + `CatalogPicker` | если у зеркал появятся позиции поставщиков |
| `saveCalculation` → `mglass_kp_prefill` → `/kp` | тот же путь к КП, что у душевых |

## Маршрут

### З1. Подменю продукта в «Расчёте»
`/calculator/build` получает верхний переключатель **Душевые · Зеркала · Лофт**.
Экран 1 (выбор модели) становится общим: карточки моделей текущего продукта.
Душевые не трогаем — их ветка остаётся как есть.
*Готово, когда:* переключатель есть, душевые работают как раньше, зеркала ведут на З2.

### З2. Модели зеркал (справочник, не код)
Порядок владельца: **обычное зеркало → зеркало с подсветкой** → дальше расширяем
(в металлической раме, круглое и т.д.). Модель = карточка с фото + набор параметров,
которые она открывает. Хранить как данные (таблица `mirror_models`), чтобы добавление
модели не было релизом.
*Готово, когда:* две модели в базе, карточки с фото, выбор ведёт на З3.

### З3. Геометрия зеркала → количества
Аналог `computeKitQuantities` у душевых: из размеров и выбора сторон подсветки получаем
**длину подсветки, периметр, площадь, точки БП и вывода провода**. Сейчас геометрия
дублируется в трёх файлах — здесь она становится одна и кормит и расчёт, и картинку.
*Готово, когда:* функция чистая, покрыта тестом, зовётся и расчётом, и визуалом.

### З4. Кратность расходников — бухты и хлысты
Правило владельца: **нужно 3 м ленты → расходуется бухта 5 м, платим за бухту.**
То же для профиля и рассеивателя (хлысты). Образец — `planBars` и `calcFrameCost`.
Требует поля длины бухты/хлыста в `mirror_lighting_components`.
*Готово, когда:* в спецификации видно «лента 5 м × 1 бухта», а не «3 пог. м».

### З5. Серверный роут `POST /api/calc/mirror`
По образцу `/api/calc/build`: композиция двух движков — **зеркало по B2B-цене со скидкой
M GLASS** (как стекло у душевых, «почём для M-Glass»), **подсветка и рамка — своим составом**
из справочников. Себестоимость наружу не отдаём. Возвращаем спецификацию строками
(что, сколько, по чём) — как в душевых после #465.
*Готово, когда:* цена считается на сервере, в браузере нет ни одного `cost_price`.

### З6. Экран расчёта зеркала
Слева визуал (пока 2D-SVG `generateMirrorSVG`, 3D — отдельный вопрос), справа параметры:
размер → тип зеркала/толщина → подсветка (стороны, температура, управление) → рамка
(Ветро / металлическая антирамка / П-профиль — **последний требует 6 мм**, иначе не сядет:
блокируем выбор) → фацет/пескоструй → маржа/налог/монтаж/доставка. Внизу «+ Ещё изделие»
и «Сохранить → КП», как у душевых.
*Готово, когда:* менеджер считает зеркало, не открывая старый экран.

### З7. Админка «Себестоимость визуализатора зеркал»
По образцу `/admin/visualizer-pricing` (душевые): роль → позиция → цена. Роли зеркала:
лента, профиль, рассеиватель, БП, кнопка/сенсор, провод, коннекторы, рамка(3 вида),
подложка, упаковка. Цены — из справочника закупки, не из кода.
*Готово, когда:* новую ленту или рамку заводит владелец без разработчика.

### З8. Одно КП из разных продуктов
Корзина «Расчёта» принимает и душевую, и зеркало; КП собирается из позиций разных
продуктов с картинками. Путь тот же: `mglass_kp_prefill` → `/kp` → сделка.
*Готово, когда:* в одном КП душевая и зеркало, обе с фото.
