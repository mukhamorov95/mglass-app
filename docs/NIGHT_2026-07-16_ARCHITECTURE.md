## 1. АНАЛИЗ (по факту кода, 5 параллельных исследований)

### 1.1 Детерминизм цены — источник НЕ единый
Функция расчёта душевой одна — `calculateShower` (`lib/showerCalculator.ts`). Но AI (`lib/quickCalc.ts`) и UI (`app/calculator/shower/page.tsx`) **кормят её разными входами**:

| Вход | UI (эталон) | quickCalc (AI) сейчас | Итог |
|---|---|---|---|
| Расходы (знаменатель) | `financial_settings.tax_percent` = **12%** | `TIER_CONFIGS.expensesPercent` = **33%** | делитель 0.48 vs 0.27 → **×1.78** |
| Стекло | `glass_price_matrix` sale t8 = **3258** | `materials.cost_price` (пусто → **3000**) | занижение себестоимости |
| Маржа | `owner_strategy.target_margin` = 40 | `financial_settings.default_margin` = 40 | совпадает случайно |
| Фурнитура (бюджет) | `shower_budget_manual_prices` → иначе формула | только формула | расходится при заполнении таблицы |
| Модель | таблица `shower_models` | константа `SHOWER_MODELS` | могут разойтись |

**Проверено на проде:** M2 900×2000 бюджет хром → UI **28 467 ₽**, AI **48 889 ₽** (+72%). Доминирующая ошибка — расходы 33% вместо 12%.

### 1.2 Себестоимость фурнитуры
Бюджет-фурнитура уже живёт в `shower_budget_manual_prices (model_id, color_id → price)`, но **заполнена одна строка (M10/хром=10000)**; остальные модели идут по формуле `hardware_base × 0.6 × цвет`. Редактора нет — Вера не может выверить.

### 1.3 CRM / Авито
`crm_leads` — вебхук уже создаёт лида по `avito_chat_id`. Импорта существующих чатов нет. Нужны GET-функции Avito Messenger API (`/core/v1/accounts/self`, `/messenger/v2/.../chats`, `/messenger/v3/.../messages`) + классификатор «интересно/отказ». Риск: скоуп `messenger:read` у client_credentials — проверяется живым запросом, деградируем мягко.

### 1.4 Продажи / РОП
`/manager-dashboard` уже даёт менеджеру выручку+маржу (B2B). `/my-earnings` — B2C-комиссии. `/commercial` (РОП) — только активность из AmoCRM, **денег/маржи нет**. Данные о продажах разбросаны: `calculations` (B2C), `b2b_orders` (B2B). `fetched_sheet.csv` — внешняя мастер-таблица «отдела продаж» (дневная воронка/оплаты по менеджерам) — ТЗ на метрики.

### 1.5 Отдел реализации
Два несвязанных контура монтажа (`installations` новый / `appointments` старый) и два «замера» (`measure_requests` / `measurements`). Нет сквозного объекта продажа→замер→производство→монтаж (связь только текстовым номером). «Согласуем замер» из чата не превращается в заявку.

### 1.6 Скорость
Корень «подвисаний» — **водопад 3–4 последовательных `auth.getUser()` + запросов профиля на каждой навигации**, ноль кэширования (`0` `unstable_cache`/`cache()`/`Suspense`), синхронная тяга **всех** сделок AmoCRM при рендере дашбордов. Бандлы и тяжёлые либы — уже правильно (динамический import). Sentry Replay висит на клиенте.

## 2. РЕШЕНИЕ (архитектура)

### Спайн детерминизма (ядро)
Единственный источник входов душевой — новый чистый модуль **`lib/pricing/showerInputs.ts`**: резолверы `resolveShowerGlassCostPerM2`, `resolveShowerExpensesPercent`, `resolveBudgetHardwareCost` + общие константы `GLASS_MATRIX_NAME`, `COLOR_DB_NAME`. И `quickCalc`, и UI зовут ОДНИ резолверы → одинаковые входы → одинаковая цена. Покрыто golden-тестом (M2 900×2000 бюджет = 28 467 ₽).

### Себестоимость фурнитуры для Веры
Экран `/admin/shower-hardware`: таблица 12 моделей × бюджет-цвета, редактируемая себестоимость фурнитуры → upsert в `shower_budget_manual_prices` (owner/cfo-gated API). Калькулятор показывает «Стекло X · Фурнитура Y» с ссылкой на редактор. Иван (quickCalc) читает те же выверенные числа.

### Иван
Персона Максим → **Иван**. Просчёт — только через `quickCalc('shower', …, {tier:'budget'})` = тот же душевой-бюджет калькулятор. Никаких цен «из головы» (уже так: метки `{{PRICE_n}}`).

### Продажи / РОП
`/api/commercial/money` — агрегат по менеджеру за месяц (выручка+маржа+средний чек), объединяя `calculations` + `b2b_orders`. Секция-лидерборд в `/commercial`. Кабинет менеджера с продажами уже есть (`/manager-dashboard`).

### Скорость (быстрые победы, безопасно)
1. `React.cache()` вокруг `getUser/getUserProfile/getRole` → один `getUser()` на рендер.
2. Кэш `getPipelines/getUsers` AmoCRM (`revalidate 3600`).
3. Снять Sentry Replay с клиента.
4. Проверить/докатить перф-индексы.

### Отдел реализации / Авито-импорт
Проектируется здесь, внедряется по остаточному приоритету ночи (см. отчёт). Реализация — единая группа меню + AI→черновик замера; Авито-импорт — GET-функции + классификатор + экран, мягкая деградация по скоупу.

## 2.1 Отдел реализации — рекомендация (проектное решение)

**Вопрос владельца:** нужен ли отдельный кабинет «Отдел реализации» (замерщики + монтаж + учёт объектов), синхронизировать ли Google-таблицу или вести всё в программе.

**Что есть сейчас (по аудиту кода):**
- Замеры — полный контур на `measure_requests`: заявка менеджера (+AI-разбор диктовки) → пул → замерщик берёт/назначает/закрывает → календарь → учёт денег замерщика. Роль `measurer` заведена.
- Монтаж — полный контур на `installations` + `installation_crews`: заявка, копия в чат, Google-календарь, статусы, суммы бригад.
- **Проблемы:** (1) живут ДВА монтажных контура (`installations` новый / `appointments` + `/admin/installations` старый) и ДВА «замерных» (`measure_requests` / легаси `measurements`); в меню два пункта «Монтажи» на разные страницы. (2) Нет сквозного объекта: продажа→замер→производство→монтаж связаны только текстовым номером заказа, без FK и без единого статуса. (3) «Согласуем замер» из чата Ивана не превращается в заявку `measure_requests` — менеджер заводит вручную.

**Рекомендация (ответ: ДА, нужен единый кабинет, но эволюционно):**
1. **Меню-группа «Реализация»** (не новая БД): собрать под один аккордеон `/installations`, `/measure-requests`, `/measure-calendar`, `/measurer-cabinet`, `/admin/brigades`; убрать дубль — старый `/admin/installations` вести как редирект на `/installations` после сверки, что там нет уникальных данных.
2. **Сквозной объект — минимальным швом:** ввести общий `order_no` как ключ (UNIQUE) и добавить nullable-FK `object_ref` в `measure_requests`, `installations`, `b2b_orders`/`crm_leads`. Тогда один экран-реестр «Объекты в реализации» показывает статус: лид → замер назначен/проведён → в производстве → монтаж назначен/закрыт. Это отдельный трек (миграция + бэкофилл), НЕ ночью — риск для 679 исторических.
3. **AI→замер:** добавить в схему рантайга Ивана флаг `proposes_measure`; вебхук при нём создаёт черновик `measure_requests` (status `new`, из снятых имя/телефон/город) — договорённость из чата попадает в пул автоматически.
4. **Google-таблица продаж (`fetched_sheet.csv`):** цель — отказаться от неё, ведя всё в программе. Дневная воронка/оплаты по менеджерам уже частично покрыты (`/commercial` активность + новый лидерборд денег). Полное замещение = перенести дневные метрики заявок/конверсий в БД (таблица `sales_daily` по менеджеру×каналу×дню) + импорт истории из CSV. Отдельный трек.

**Вывод:** кабинет «Реализация» = группировка существующих контуров + сквозной объект. Ночью сделана только безопасная часть (документ-решение). Внедрение — по одному шву за раз, с проверкой на исторических данных.
