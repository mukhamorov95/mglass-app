# Оркестрация вкладок M-Glass — живой реестр

> **Зачем.** Над M-Glass App параллельно работают несколько сессий Claude («вкладок»). 25.08 мы
> дважды начинали строить то, что уже готово (складской контур `/inventory`, ссылки-приглашения) —
> спасла только ручная проверка. Этот файл — единый источник правды «кто чем занят» + открытые
> межвкладочные передачи, чтобы не дублировать и не ломать чужое.
>
> **Правило.** Перед работой в чужом домене — свериться здесь. После значимого шага — дописать
> строку (карта или лог). Синхронизацию ведёт backbone-сессия (оркестратор).
>
> Смежные доки: `docs/CONFIGURATOR_COORDINATION.md` (граница Сайт+3D ↔ Прайс),
> `docs/WAREHOUSE_ARCHITECTURE.md` (склад), `docs/INVENTORY.md` (реализация склада).

## Открытые межвкладочные передачи (кто → что нужно сделать)

   привязывает** пользователя к юрлицу-заказчику (`b2b_clients.user_id`). Без привязки первый вход
   партнёра — пустой кабинет. Нужно: при выдаче инвайта партнёру связать/создать `b2b_clients`
   (онбординг — территория партнёрской вкладки, см. `docs/PARTNER_CABINET_ONBOARDING.md`).
   **Статус: открыто, исполнителя нет** (партнёрская вкладка не активна).

2. **→ Склад (/inventory) + backbone.** Шаг **С4**: резерв материала при запуске заказа.

   «что забрать / что купить» на экране запуска. Контракт: **best-effort** — ошибка склада не
   блокирует запуск заказа (иначе при пустом контуре встало бы производство).
   ⚠️ Никому больше этот хук не брать — на нём уже двое.

## Правила, выработанные на практике (обязательны для всех вкладок)

Каждое родилось из конкретной ошибки или находки — не выдуманы, ссылки на случай приведены.

1. **Метрику строим на том, что люди уже делают, а не на том, что мы надеемся их заставить.**
   Кнопка «Взял в работу» существовала и собрала 0 нажатий за 2 месяца. «Время этапа» изначально
   стояло на этом сигнале — переставлено на интервал между двумя подряд «Готово» одного человека
   на одной станции: считается из того, что цех делает добровольно.

2. **Кнопка, которая создаёт человеку работу, использоваться не будет.**
   `problem` = 0 при 3670 задачах не разгильдяйство: отметка вынимала задачу из потока, и её же
   потом надо было закрывать на отдельной доске. Контрпример в той же системе: «нет материала»
   используется (83 заказа), потому что даёт результат — заказ уходит в закупку. Проверяй шаг
   вопросом «что человек с этого получит», а не «сколько это кликов».

3. **Признак без данных обязан молчать, а не кричать.**
   Долг перед отгрузкой зажигается только при частичной оплате (0 < оплачено < сумма); ноль
   платежей = «оплата не заведена», не «должник». Иначе на 5000 заказов без импорта выписки
   система кричала бы на всё подряд и её перестали бы читать.

4. **Процент по узкой выборке нельзя показывать без покрытия.**
   «В срок %» считался честно, но по 13% отгрузок (у остальных дата не сохранялась) — и «из 267
   заказов» читалось как «почти все». Рядом с процентом всегда доля покрытия.

5. **Если проверку физически нельзя сделать — назови её невыполнимой и перечисли, что проверено
   вместо неё.** Имитация проверки хуже её отсутствия: снимает вопрос, не отвечая на него.
   (verified-by-code-path вместо живого SELECT на пустом складе.)

6. **Автоматическая запись не должна выдавать план за факт.**
   Движения склада несут `origin`: `plan` (списано по резерву) против `fact` (человек подтвердил).
   Без пометки остаток снова стал бы фикцией — только красивой и незаметной.

7. **Побочный системный эффект пишем server-only функцией, а не расширением прав человека.**
   Списание при отметке «упаковано» идёт через `consumeForOrder` (`import 'server-only'`), а не
   добавлением менеджера в `requireInventoryWrite` — иначе он смог бы править остатки напрямую.
   Прецедент: `reserveForOrder` на `launch-production`.

8. **`notes.stages` — общая свалка производства, отгрузки и денег** (`shipped` 4375, `invoice_paid`
   90, производственные этапы). Трогать оттуда можно ТОЛЬКО ключи своего контура и только через
   явный белый список, никогда «снимем всё, что переоткрыли».

9. **Тестовые данные в боевой базе не создаём.** Они переживают задумку, и через месяц их не
   отличить от настоящих; инвентаризация владельца должна начинаться с нуля, а не с чужих чисел.

10. **Настройки прав и доступа не едут в продуктовых PR.** Права меняются решением владельца
    осознанно, а не «заодно». (Файл авто-разрешений на `git push`/`gh pr merge` проехал в main
    внутри продуктового PR и был вычищен отдельно.)

11. **Историю не выдумываем.** Дату отгрузки для 3788 заказов с голым `true` восстановить неоткуда;
    исполнителя для 137 отметок без `updated_by` — тоже. Пустое поле честнее выдуманного.

12. **Перед пушем подтягивай main.** Десять параллельных вкладок мержат быстрее, чем одна успевает
    ребейзить; окно между «чисто» и «снова разошлось» — минуты. Ребейзнул → пингани оркестратора
    одной строкой «#N чист», мерж идёт сразу. (Авто-мерж в репозитории запрещён настройкой —
    владельца просили включить.)
