# Маршрут: команда партнёра в кабинете B2B

Задача владельца (24.11.2026). Выдать кабинет Шовер Гласс так, чтобы у каждого их сотрудника был свой вход:

* руководитель, менеджер, бухгалтер, кладовщик;
* мы даём один доступ — руководителю, дальше он сам выдаёт доступы своим людям;
* мы видим, сколько у них людей, кто они (имя, логин) и кто как часто пользуется кабинетом. Пароли не видим никто и никогда.

Маршрут продолжает `docs/B2B_CLIENT_CABINET.md` (кабинет и изоляция) и A6 из `partner-cabinet-roadmap` (`b2b_client_members`, где пока все участники равны).

## Цель

Проверка — три вопроса, на каждый ответ с одного экрана:

1. **Руководитель партнёра:** кто из моих людей имеет вход и что каждый может; добавить человека — минута.
2. **Сотрудник партнёра:** видит ровно свою часть. Кладовщик — заказы и отгрузки без цен, бухгалтер — деньги и документы.
3. **Мы (владелец):** у клиента N человек, кто они, когда каждый заходил, сколько дней из 30 и сколько просчётов сделал.

## Структура кабинета (что видит партнёр)

| Раздел | Что внутри | Сейчас |
|---|---|---|
| Табло | что ждёт действия, последние события, экономия | есть |
| Калькулятор → Новый просчёт | цены партнёра (скидка карточки или индивидуальный прайс) | есть |
| Мои просчёты | черновики, согласованные, отправленные в работу | есть |
| Заказы в работе | этап цеха, срок, **оплата** | есть, оплата с #1111 |
| Отгруженные | что уехало, УПД | есть |
| Документы | счета, УПД | есть |
| Профиль | юрлица и реквизиты | есть |
| Гарантия | претензии | есть |
| **Команда** | люди компании, роли, приглашения | **нет — этот маршрут** |

## Как устроено сейчас (24.11)

* Один логин = одна компания: `b2b_clients.user_id` — первичный, `b2b_client_members` — остальные (`UNIQUE(user_id)`). Все равны, ролей нет.
* Добавляет людей только владелец: `/admin` → доступ B2B (`/api/admin/b2b-access`), ссылка на пароль через `user_setup_tokens`.
* Активность уже пишется у всех: `user_activity_days` (первый и последний заход за день, из middleware) и `user_devices`.
* Автор просчёта пишется (`b2b_orders.created_by`), но имя — название компании, а не человека.
* Шовер Гласс (`b2b_clients.id=2`): логина нет, людей нет.

## Роли и права (одна матрица — `lib/partner/teamRoles.ts`)

| Право | Руководитель | Менеджер | Бухгалтер | Кладовщик |
|---|---|---|---|---|
| Видеть заказы, этапы, сроки, отгрузки | ✓ | ✓ | ✓ | ✓ |
| Видеть цены и суммы | ✓ | ✓ | ✓ | — |
| Калькулятор, просчёты, отправка в работу, согласование чертежа | ✓ | ✓ | — | — |
| Оплаты, счета, УПД, реквизиты | ✓ | статус оплаты | ✓ | — |
| Получение и доставка | ✓ | ✓ | — | ✓ |
| Гарантия (претензии) | ✓ | ✓ | — | ✓ |
| Команда: пригласить, сменить роль, отключить | ✓ | — | — | — |

Права проверяет **сервер** (`/api/partner/*`), а не меню: кладовщику цены не приходят в ответе, а не прячутся на экране.

## Этапы

### Т1. Роли в базе и проверка прав на сервере — СДЕЛАНО 24.11
`b2b_client_members.role` (`admin | manager | accountant | storekeeper`), `name`, `disabled_at`. Первичный владелец карточки — руководитель. Один резолвер `resolvePartnerMember()` отдаёт компанию, роль и права; все маршруты кабинета берут права из него. Цены вырезаются из ответа для ролей без права «цены».
**Проверка:** тест матрицы на каждый маршрут; запрос под кладовщиком не содержит сумм.

### Т2. «Команда» у руководителя партнёра — СДЕЛАНО 24.11 (на проде не проверено приглашением)
`/partner/team`: список людей (имя, логин, роль, последний вход), «Пригласить» (имя, email, роль → ссылка на пароль, которую руководитель отправляет сам), сменить роль, отключить. Лимит мест на компанию (`b2b_clients.max_members`, по умолчанию 10). Себя отключить и последнего руководителя разжаловать нельзя.
**Проверка:** приглашение → вход по ссылке → человек видит свою часть.

### Т3. Наш обзор команды клиента — СДЕЛАНО 24.11 (`/admin/b2b-access` → «Команда»)
В карточке клиента у нас: люди, роль, логин, кто пригласил, последний вход, дней активности за 30, просчётов и отправленных заказов. Пароли не хранятся в открытом виде и не показываются.
**Проверка:** цифры сходятся с `user_activity_days` и `b2b_orders.created_by`.

### Т4. Автор действий в кабинете — СДЕЛАНО ЧАСТИЧНО 24.11: новый просчёт пишет «Компания · Имя»; в кабинете автор пока не показан
Просчёт и заказ подписаны человеком («Просчёт — Иванова»), а не названием компании.

### Т5. Выдача Шовер Гласс
Владелец заводит руководителя (email руководителя Шовер Гласс), отдаёт ссылку на пароль. Письмо клиенту отправляет владелец сам.

## Решения владельца

1. Матрица прав выше — по умолчанию. Менять — одна строка в `lib/partner/teamRoles.ts`.
2. Лимит мест: 10 на компанию бесплатно. Платные места — к `cabinet-monetization`, если решите.
3. Приглашение — ссылкой, которую руководитель партнёра пересылает своему человеку сам; мы писем не шлём.

## Грабли

* Триггер `handle_new_user` давал каждой новой учётке роль `manager` (сотрудник). Роль партнёра ставилась отдельной записью после создания — сбой между ними оставил бы внешнему человеку внутренние права. С 24.11 учётка из приглашения рождается партнёром (`app_metadata.mglass_kind = 'partner'`), а приглашение проверяет роль и при сбое удаляет учётку.
* Выдача доступа владельцем по email существующего человека переводила его в партнёры — и нашего сотрудника тоже. С 24.11 отказ.
* `auth.admin.signOut` в supabase-js принимает JWT, а не id пользователя: отключение работает через резолвер (`disabled_at` проверяется на каждом запросе), а не через разлогин.

## Риски

* Отключённый человек с живой сессией: отключение проверяется в резолвере на каждом запросе, а не только при входе.
* Роль меняется у вошедшего — действует со следующего запроса (резолвер читает базу, кэша нет).
* Руководитель партнёра может пригласить email, уже занятый нашим сотрудником или другой компанией, — отказ (`UNIQUE(user_id)` и проверка роли).

## Потолок

* Тонких прав «по объекту» (менеджер видит только свои заказы) нет — все в компании видят все заказы компании в пределах роли.
* Активность — дни и время входа, а не каждый клик.
