## Цель

Каждое событие заказа (оплата, упаковка, отгрузка, УПД) отмечается один раз, в момент события, тем, кто его видит, — и сразу доходит до всех, кому оно нужно: менеджеру, цеху, бухгалтеру, партнёру, владельцу. Мерило готовности — три числа, сверяемые запросом:

* упакованных B2B-заказов без отметки «отгружен» старше 7 дней — **0** (сейчас 78);
* счетов «ждут оплаты», которые по платежам уже оплачены, — **0** (сейчас 37 на 839 829 ₽);
* одна цифра долга и выручки месяца на всех экранах владельца (сейчас долг 0 ₽ против 4,83 млн ₽; выручка сентября 0 / 0,96 / 4,44 млн ₽).

## Этапы

Порядок — по отдаче: сначала то, что возвращает деньги и правду о деньгах. Каждый этап — точка остановки.

### 1. Одна правда о деньгах по заказу — ЖДЁТ
Оплата — только таблица `payments` (единственный писатель `recordPayment`).
* Статус счёта вычисляется из платежей; кнопки «Оплачен» в `components/accounting/DocumentsTab.tsx:114` и `/cfo/invoices` идут через маршрут оплаты.
* Ручное «Оплачен» в `app/api/b2b-orders/[id]/payment/route.ts:96-104` видит уже пришедшие платежи — второго платежа нет.
* Неоплаченный счёт обновляется при смене суммы/юрлица (`app/api/invoices/route.ts:156-161` сейчас отдаёт старую запись); заказ не попадает в два счёта.
* Долг на /ceo, /cfo/receivables, прогноз кассы, `cron/morning-briefing` — одной функцией (`lib/b2b/orderPayments.ts`).
* Шапка и метка оплаты в /b2b-orders — из платежей, а не из флажков (`app/b2b-orders/page.tsx:351-363`).
**Проверка:** три числа из «Цели» по деньгам сходятся запросом. **Риск:** средний — трогает деньги; каждая правка с тестом на сумму. Размер M.

### 2. Отгрузку отмечают в день отгрузки, следом — УПД — ЖДЁТ

* «Мой день · B2B»: группы «Готов, не отгружен» и «Выдать УПД» (`lib/b2b/updQueue.ts` сейчас только у бухгалтера).
