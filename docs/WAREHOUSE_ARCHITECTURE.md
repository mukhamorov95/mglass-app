# Склад / остатки — архитектура модуля

> Статус: спека для новой вкладки «Склад». Greenfield — сейчас склад не ведётся вообще.
> Охватывает **и B2B, и B2C**. Механизм единый; разница только в поведении (что чаще «лежит», а что «покупаем под заказ»).
> Себестоимость — CFO-территория: числа стоимости отдаём только ролям owner/cfo/buyer, клиенту/менеджеру не утекает.

## Зачем

Сегодня «что где купить и что где забрать» держится в голове логиста и снабженца. Цель — чтобы при запуске
заказа система **сама раскладывала потребность на: забрать со склада / докупить у поставщика**, а остаток
считался не «числом, которое кто-то поправил», а **из журнала движений** (аудируемо, без потерь).

## Принципы

1. **Остаток = сумма движений, а не поле.** Никаких «кто-то поменял число». On-hand = Σ(движений). Любое
   изменение — строка в журнале (приход/расход/корректировка). Это убирает класс ошибок «остаток разошёлся».
2. **Резерв ≠ расход.** Запуск заказа *резервирует* материал (available = on-hand − резерв). Списание —
   отдельное движение, когда материал реально взяли в цех.
3. **Дефицит рождает закупку.** Если резерв > наличия → позиция в дефиците → попадает в заявку на закупку
   к нужному поставщику. Это и есть авто-разбивка «купить vs забрать».
4. **Мягкое внедрение.** Каждый шаг маршрута полезен сам по себе. Начинаем с «что и сколько лежит» — без
   заказов, без резервов. Связку с заказами добавляем позже.
5. **Один механизм для B2B и B2C.** Поведение (лежит/покупаем) определяется остатком и точкой заказа, а не
   отдельной логикой по контурам.

## Ключевые сущности

| Сущность | Смысл |
|---|---|
| **Номенклатура** (`warehouse_items`) | Складская позиция (SKU): стекло, зеркало, профиль/АП-профиль, фурнитура, уплотнитель, расходник. Ед. изм., категория, точка заказа. Ссылка на позицию(и) справочника поставщиков. |
| **Движение** (`stock_movements`) | Любое изменение остатка: приход, расход, возврат, корректировка, перемещение. Знак qty + тип + причина + ссылка на заказ/закупку + себестоимость. **Остаток выводится отсюда.** |
| **Резерв** (`stock_reservations`) | Бронь под конкретный заказ. `available = on_hand − Σ активных резервов`. |
| **Заявка на закупку** (`purchase_requests` + строки) | Что докупить, сгруппировано по поставщику. Рождается из дефицита. |
| **Приёмка** (движение типа `purchase`) | Приход по заявке (или вручную) — увеличивает остаток, закрывает дефицит и резерв. |
| **Локация** (`warehouse_locations`) | Опционально. Стартуем с одним складом по умолчанию; поле закладываем на будущее. |

## Модель данных (эскиз)

```
warehouse_items
  id, sku, name, category('glass'|'mirror'|'profile'|'hardware'|'seal'|'consumable'|...),
  unit('шт'|'м.п.'|'м2'|...), min_qty numeric default 0, is_tracked bool default true,
  default_supplier text null, supplier_catalog_ids int[] null, created_at

stock_movements                         -- источник правды по остаткам
  id, item_id → warehouse_items, location_id null,
  qty numeric,                          -- +приход / −расход
  type('purchase'|'consume'|'return'|'adjust'|'transfer'),
  order_id text null,                   -- если списание/резерв под B2B/B2C заказ
  purchase_id null,                     -- если приход по заявке
  unit_cost numeric null,               -- себестоимость единицы (CFO-gated в выдаче)
  note text null, created_by, created_at

stock_reservations
  id, item_id → warehouse_items, order_id text, qty numeric,
  status('active'|'released'|'consumed'), created_at, released_at null

purchase_requests
  id, supplier text, status('draft'|'ordered'|'received'|'canceled'),
  order_id text null, created_by, created_at
purchase_request_lines
  id, request_id → purchase_requests, item_id → warehouse_items, qty numeric, unit_cost null

warehouse_locations (future)
  id, name, is_default bool
```

**Производные (view):**
```
v_stock_onhand   = Σ stock_movements.qty            group by item_id
v_stock_reserved = Σ stock_reservations.qty (active) group by item_id
доступно (available) = on_hand − reserved
статус позиции: available < 0 → 'дефицит'; available < min_qty → 'ниже минимума'; иначе 'норма'
```

Себестоимость: средняя по приходам (moving average) из `unit_cost`. FIFO — на будущее, если понадобится.

## Основные процессы

### 1. Запуск заказа → резерв + дефицит  *(шов с launch-production — backbone)*
```
для каждой позиции спецификации (BOM) заказа:
    avail = on_hand(item) − reserved(item)
    reserve = min(need, max(avail, 0))
    if reserve > 0: создать резерв (status=active)          → «забрать со склада»
    deficit = need − reserve
    if deficit > 0: строка в заявку на закупку(supplier)     → «купить у поставщика»
```
Результат — готовый список логисту/снабженцу: *забрать* (по позициям) + *купить* (по поставщикам).

### 2. Закупка → приёмка
```
заявка(draft) → отправлена(ordered) → приход:
    движение type=purchase, qty=+принято, unit_cost=цена
    → on_hand растёт → дефицит закрывается → резерв под заказ становится обеспеченным
```

### 3. Производство берёт материал → списание
```
движение type=consume, qty=−взято, order_id=заказ
резерв заказа → status=consumed
```

### 4. Инвентаризация → корректировка
```
факт vs учёт → движение type=adjust на разницу (с причиной)
```

### 5. B2B vs B2C — одинаково
Разница только в исходных остатках и точках заказа:
- **B2C:** большинство позиций держим по нулям → почти всё уходит в «купить». Профили/АП-профиль лежат →
  «забрать».
- **B2B:** так же; часть ходовых комплектующих можно держать, чтобы не тормозить запуск.
Никакой отдельной ветки кода — поведение задаётся данными (остаток + `min_qty`).

## Разделы вкладки «Склад» (UI)

1. **Остатки** — таблица: позиция · наличие · зарезервировано · доступно · точка заказа · статус
   (норма/ниже минимума/дефицит). Фильтр по категории. Это главный экран.
2. **Движения** — журнал приходов/расходов/корректировок (лента, фильтры).
3. **Закупки** — заявки, сгруппированные по поставщику (из дефицитов + ручные). Статусы.
4. **Приёмка** — оформить приход (по заявке или вручную).
5. **Инвентаризация** — сверка факта, корректировки.
6. **Карточка позиции** — история движений, поставщики, себестоимость, график остатка.

## Роли и доступ

- **Закупщик** — заявки, приёмка, номенклатура, остатки.
- **Логист** — что забрать/докупить под заказ, движения.
- **Производство** — списание материала под заказ.
- **owner/cfo** — всё + себестоимость и отчёты.
- **Менеджер/клиент** — НЕ видят склад и себестоимость.

Складская роль: переиспользуем `buyer` (закупщик) как основную; списание из цеха — под `production`;
стоимость в выдаче гейтим по owner/cfo/buyer. Числа `unit_cost`/`avg_cost` НИКОГДА не уходят в
менеджерские/клиентские/партнёрские API.

## Границы с другими вкладками (во избежание коллизий)

- **Справочник поставщиков и цены** — территория вкладки «Прайс» (`app/admin/supplier-catalog/**`,
  `app/api/admin/supplier-catalog/**`). Склад **ссылается** на позиции справочника (`supplier_catalog_ids`)
  и берёт оттуда цену/поставщика, но сам справочник не редактирует. Контракт: Прайс владеет ценой,
  Склад владеет остатком.
- **Запуск заказа** (`app/api/b2b-orders/[id]/launch-production/route.ts`) — backbone-сессия. Хук резерва
  (процесс №1) добавляет backbone; вкладка «Склад» отдаёт функцию `reserveForOrder(orderId, bom)` и таблицы.
- **CFO** — потребляет себестоимость движений для маржи/P&L (роль-гейт).

## Маршрут внедрения (мягкий, каждый шаг самостоятелен)

| Шаг | Что | Польза сразу |
|---|---|---|
| **С1 · Номенклатура + стартовые остатки** | Завести позиции (можно импортом из справочника поставщиков), проставить «что и сколько лежит» инвентаризацией | Впервые видно, что есть на складе |
| **С2 · Движения (приход/расход вручную)** | Кнопки «принять» / «списать» → журнал; остаток считается из движений | Остаток перестаёт врать |
| **С3 · Точка заказа + дефицит** | `min_qty` → подсветка «ниже минимума» + список «надо купить» | Не забываем закупить ходовое |
| **С4 · Связка с заказом (резерв)** | При запуске — резерв под BOM, дефицит → заявка. **«Что купить / что забрать»** | Снабжение перестаёт жить в голове |
| **С5 · Закупка → приёмка** | Заявка по поставщику → приход закрывает дефицит и резерв | Полный цикл закупки в приложении |
| **С6 · Инвентаризация + себестоимость** | Сверка, средняя цена, отчёт для CFO/маржи | Точный склад + деньги в маржу |

## Открытые вопросы (уточнить у владельца по мере внедрения)

1. **Единицы и раскрой.** Профиль/стекло ведём в м.п./м²? Раскрой (хлысты) уже считает Прайс — склад берёт
   потребность из BOM в тех же единицах.
2. **Локации.** Один склад или несколько точек (склад + цех + машина логиста)? Заложено полем, включаем при
   надобности.
3. **Кто списывает в цехе.** Списание по факту (рабочий отмечает) или списывать при запуске? Рекомендация —
   резерв при запуске, списание по факту (точнее себестоимость).
4. **Стартовые остатки.** Как заносим первый раз — разовая инвентаризация вручную или импорт из чего-то?
