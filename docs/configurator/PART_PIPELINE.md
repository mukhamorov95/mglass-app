# Как заводится новая деталь фурнитуры в 3D

Инструмент узкий и намеренно скучный: ссылка на товар + фото + чертёж → паспорт детали →
приёмка на стенде → деталь стоит в конфигураторе там, где нужно. Ошибиться можно только
в одном месте — в числах с чертежа, и именно это место проверяется глазами и тестом.

## Что присылает владелец

Три вещи, лучше одним сообщением:

1. **Ссылка** на карточку товара у поставщика (артикул, цвет, под какое стекло).
2. **Фото** детали — чтобы силуэт был узнаваемым, а не «кубиком».
3. **Чертёж с размерными линиями** — единственный источник чисел. Без него деталь не заводится:
   модель по «примерно на глаз» выглядит правдоподобно и потому опаснее, чем её отсутствие.

Если чертежа у поставщика нет — скажите, поставим деталь прежней обобщённой формой
и пометим в конфигураторе «вид угадан», а не сделаем вид, что знаем размеры.

## Что происходит дальше

| Шаг | Где | Что получается |
|---|---|---|
| 1. Разбор | `POST /api/configurator/part-draft` (только админ) | Черновик паспорта + список «чего не видно на чертеже» |
| 2. Сверка | я вручную, против чертежа | Числа подтверждены размерными линиями, лишние выброшены |
| 3. Паспорт | `lib/configurator/parts/catalog/<артикул>.ts` | Деталь как данные: размеры, геометрия, посадка |
| 4. Приёмка | `/admin/hardware-studio` | Деталь рядом со своим чертежом, на своей поверхности |
| 5. Связь с прайсом | поле «вид» у позиции справочника | Деталь встаёт там, где стоит эта позиция комплекта |

Шаг 1 не обязателен — паспорт можно написать сразу руками. Он экономит время на деталях
с плотным чертежом и всегда честно перечисляет, чего на чертеже не хватает.

## Паспорт детали

```ts
export const SD_210_L230: PartSpec = {
  id: 'handle-bar',              // ключ формы — он же в поле «вид» справочника
  article: 'SD-210/L230',        // как в прайсе
  role: 'handle',                // роль комплекта
  source: { drawing: '/configurator/hardware/sd-210.jpg' },   // откуда числа
  dims: { reach: 60, gripLen: 190, boltPitch: 210, … },       // всё в мм, с чертежа
  geometry: [ { p: 'box', size: [20, 20, 60], at: [0, 105, 30] }, … ],
  mount: { on: 'glass-face', through: true, glassMm: [8, 10] },
}
```

### Система координат — источник половины всех ошибок

```
+Z — наружу от поверхности, на которую деталь садится
+Y — вверх
+X — вдоль поверхности
```

Ноль детали лежит **на** поверхности, геометрия растёт в **+Z**. «Вынос 60 мм» с чертежа —
это буквально `z` от 0 до 60. Знаки нигде не подбираются руками.

### Посадка

| `mount.on` | Что это | Кто так садится |
|---|---|---|
| `glass-face` | плоскость полотна | ручки, кнобы, чаши купе |
| `glass-edge` | торец полотна | петли, зажимы |
| `tube` | обхват штанги поперёк | держатели, каретки |
| `tube-end` | торец штанги | заглушки, стык к стене |
| `wall` | фланец в стену | настенные крепления |

`through: true` — сквозная двусторонняя деталь. Рисуются **две** половины, в комплекте
считается **одна** позиция: вторая помечается `mirrorOf` и пропускается при подсчёте.

## Приёмка в пять взглядов

Тот же список висит на стенде — деталь принимают глазами, и глаз должен знать, что искать.

1. **Монтажник.** С той ли стороны стоит; сквозная или зажимная; попадает ли в отверстие.
2. **Конструктор.** Каждое число сходится с чертежом; зазоры не отрицательные.
3. **Художник.** Силуэт узнаётся на фото поставщика; есть фаски, нет «кубика».
4. **Сцена.** Не проваливается в стекло и не висит в воздухе; тень падает куда надо.
5. **Прайс.** Артикул совпадает с позицией справочника; половины не считаются дважды.

## Почему это не сломает то, что работает

- **Деталь — данные, а не код.** Битый паспорт не попадает в реестр: `validate.ts` отбраковывает
  его на импорте, деталь выключается одна, сцена живёт, причина видна на стенде.
- **Старые формы не трогаются.** Нет паспорта — рисуется прежним способом (`hardware.tsx`).
  Переход подетальный, отката не требует.
- **Границы проверяются числами.** Метры вместо миллиметров, размер не того порядка,
  обойма уже трубы, деталь на чужой поверхности, стекло вне диапазона — всё это ошибки
  приёмки, а не «странно выглядит».
- **Тесты.** `__tests__/configurator/parts.test.ts` — приёмка паспорта, посадка, две половины
  сквозной ручки и то, что комплект считает её одной позицией.

## Ловушки чертежей

Собраны из разобранных ошибок, продублированы в промпте (`extractPrompt.ts`):

1. `8-10` у полотна — **толщина стекла**, а не размер детали. То же с `Ø10` у выреза:
   это отверстие в стекле.
2. Габарит ≠ рабочий размер. У П-скобы 230 — габарит, 190 — хват, 210 — межосевое.
   Три числа, каждое на своё место.
3. Двусторонняя деталь нарисована по обе стороны полотна — это одна позиция прайса.
4. Вынос считается от **плоскости стекла**, а не от края детали.
5. `30×10` у крепления — сечение **штанги**, которую оно обнимает; наружный размер обоймы
   больше на две стенки.

## Первая заведённая деталь

`SD-210/L230` — ручка-скоба. На ней инструмент и обкатан: чертёж показал, что деталь
двусторонняя (рисовали одну половину), а хват — плоская планка 20×10, а не круглый пруток.
Посадка до этого считалась арифметикой на месте установки и давала смещение по X при
нулевом смещении по Z: высота верная, ручка мимо полотна.
